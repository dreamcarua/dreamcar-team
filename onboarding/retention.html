РЕТЕНШН — розсилки клієнтам

Окремий стіл для прямих комунікацій з підписниками. Email через SendPulse, TG broadcast через бот, Push/SMS/Viber — placeholders для Phase 2.

Концепція

РЕТЕНШН — це система прямих комунікацій з клієнтською базою DreamCar (~30-40K підписників). На відміну від SMM (публічні пости у соцмережах), тут розсилка йде персонально у канал який юзер обрав: email, TG DM, push notification, SMS.

Workflow ідентичний SMM (draft → review → approved → schedule → sent), але призначення різне — повертати клієнтів які раніше купували.

Lifecycle розсилки

draft→review→approved→scheduled→sending→sent
  1. draft — створено, тільки заголовок. Тіло можна редагувати.
  2. review — надіслано на погодження. Approvers отримують DM з кнопками rmappr:y/n.
  3. approved — всі погодили. Cron retention-scheduler-5min підхоплює коли publish_at <= NOW().
  4. scheduled / sending — у процесі відправки.
  5. sent — успіх. Метрики у БД: sent_count, delivered_count, opened_count, clicked_count.
  6. failed — error message у external_error колонці.
  7. rework — повернено на доопрацювання (натиснута ↩ у TG).

SendPulse integration

🔴 HARD RULE: SendPulse READ-ONLY

Жодних змін у SendPulse через API. Тільки GET/list. Live продакшн CRM з ~50K телефонами і email — будь-який accidental DELETE катастрофічний.

Розсилка email фактично робиться через SendPulse Dashboard вручну (поки що) — система retention лише показує що готове до відправки.

TG broadcast

Канал channel='tg' з audience_list_id = TG chat_id. Edge fn retention-scheduler викликає Bot API sendMessage у вказаний канал.

Approvers / Responsibles

  • Approvers — погоджують перед запуском. Multi-select у формі. policy: all (всі) або any (один достатньо).
  • Responsibles — відповідальні за підготовку контенту. Multi-select.
  • Author — той хто створив. Зберігається у created_by.
  • Усі троє отримують DM при review/approved/rework через notify-tg v10.

Approval flow у TG

Approver отримує DM з кнопками:

  • ✓ Погодити (callback rmappr:<id>:y) — інкрементує is_approved=true. Якщо всі погодили — status=approved.
  • ↩ Повернути (callback rmappr:<id>:n) — status=rework. Approver вказує причину.
  • 🔗 Відкрити в РЕТЕНШН — лінк на pub у вебі.

Edge functions involved

  • notify-tg v10 — universal notifier для status changes
  • retention-scheduler v2 — cron */5 хв читає approved messages
  • tg-webhook — обробляє rmappr: callbacks
  • sendpulse-books-list — read-only списки SendPulse

Cron jobs

  • retention-scheduler-5min — кожні 5 хв (зміщено на :02-:57/5 щоб не колізіювати з autopost)

Troubleshooting

Approval не приходить approver-у у TG

  1. Перевір що approver має tg_chat_id у БД users (натисніть /start боту)
  2. Перевір notify-tg logs за 5 хв навколо часу status change
  3. Можливо approver заблокував бота — TG поверне 403

Розсилка не пішла у заплановний час

  1. Перевір retention_messages.status — має бути 'approved' (не 'review')
  2. Перевір publish_at <= NOW()
  3. Перевір net._http_response за останні 15 хв
  4. Перевір edge fn logs retention-scheduler
