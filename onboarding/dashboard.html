01 Концепція

Dashboard — це єдина точка істини для всіх продажів і реклами DreamCar. Замість того щоб лазити по SendPulse CRM, Facebook Ads Manager і Google Sheets — все агреговано в одну SPA з фільтрами по проектах, періодах, тарифах, traffic types.

Раніше: Make.com → Google Sheets → ручні зведення раз на тиждень. Затримка 1-2 години на синхронізацію.
Тепер: SendPulse webhook → Supabase webhook-dashboard-sendpulse Edge Function → dashboard_deals → Realtime push у браузер (< 30 секунд). FB Ads тягне Python ETL кожні 15 хвилин у GH Actions.

Чому так

Make.com з 1-годинним cron не годився для daily reporting на основі real-time. Тепер Вадим відкриває Dashboard о 9 ранку — і бачить що сталося за останні 5 хвилин.

Як працює

SendPulse → Edge Function → dashboard_deals + Realtime publication. Дані летять у клієнт через WebSocket. Materialized views із pg_cron — для важких агрегатів (3ms vs 19000ms direct LATERAL JOIN).

Ключовий принцип

RPC-перш за все. Будь-яка важка агрегація — у Postgres функції з RLS-aware. Клієнт не крутить 30k рядків у браузері — отримує готові агрегати за <100ms.

02 Архітектура

Data flow

→SendPulse CRM → webhook (pipeline_changed/deal_paid)
→Edge Function webhook-dashboard-sendpulse (verify + transform UTM)
→dashboard_deals INSERT row (Postgres + Realtime publication)
→Realtime WebSocket push → клієнти що відкрили dashboard
→debouncedReload (3s) → renderRoute() з новими даними

Окремо FB Ads — щоб не зависіти від Make.com:

→GH Actions cron */15 * * * * запускає etl/sync_fb_ads.py
→FB Marketing API v21.0 (System User Volvo_Dashboard_API, non-expiring token)
→3 Ad Accounts UAH (act_4234947706797466), CLUB USD, CLUB UAH
→Time-increment=1 day, останні 90 днів, auto-chunk >80 днів
→UTM extraction з 3 creative URL strategies (object_story_spec.link_data → url_tags → tracking_specs)
→dashboard_ads_data UPSERT (date_start, ad_account_id, campaign_id, ad_id, ...)

Performance layer (02.06.2026)

RPC дзвінки

dashboard_kpi_summary, dashboard_hourly_series, dashboard_agg_deals, dashboard_agg_deals_with_traffic, dashboard_traffic_type_summary, dashboard_kpi_with_delta. Усі параметризовані: from/to (kyiv-tz), project_values, customer_type, tariff, pay_provider, traffic_type.

Materialized views

mv_dashboard_projects_stats (агрегати по 7 проектах: deals, paid_count, revenue, conv_rate). Refresh: pg_cron кожні 5 хвилин. 3ms read vs 19000ms direct.

⚠ revoked from anon/auth 02.06 — доступ тільки через RPC.

mv_paid_signatures

Materialized view з реальними FB Ads campaign UTM signatures (matched з dashboard_ads_data). Для класифікації paid/organic. Refresh: pg_cron */15 хвилин.

Webhooks cleanup

pg_cron 0 3 * * * daily DELETE WHERE received_at < NOW() - 14 days. Запобігає 701MB IO storm.

05 Paid vs Organic logic

Раніше Dashboard міг класифікувати трафік як "paid" якщо utm_source IN ('facebook','instagram','google','tiktok') — статичний список. Проблема: частина трафіку з Instagram — органічна (stories, посилання у bio).

Тепер є mv_paid_signatures — materialized view що матчить dashboard_deals.utm_campaign із реальними FB Ads campaigns у dashboard_ads_data. Якщо UTM_campaign є у paid_signatures → paid. Інакше → organic.

→RPC is_paid_source(p_utm_source, p_utm_campaign) → boolean
→RPC is_paid_deal(p_deal_row) → boolean
→dashboard_traffic_type_summary RPC повертає paid/organic split

Результат на 02.06.2026 на тестових даних: 17-32% paid (правильно з real campaigns) vs попередньо 50/50 (статичний список).

08 Troubleshooting

Live badge не оновлюється "30s тому"

Перевір що в HTML <div class="live-badge" id="live-badge"> — id має бути. Якщо тільки клас → setupAutoRefreshIndicator мовчки виходить.

"Сьогодні" показує дані за вчора

Перевір kyivIsoStart/kyivIsoEnd helpers — мають додавати +03:00 (CEST літо) або +02:00 (CET зима). Якщо хтось знову поставив 'T00:00:00Z' — `today` рахується від UTC 00:00 = Київ 03:00.

FB Ads дані застаріли

1) Глянь GH Actions runs у dreamcar-dashboard repo — чи cron */15 працює; 2) FB token не expired (System User non-expiring); 3) Якщо потрібен force resync — workflow_dispatch з mode=range, дати on demand.

Materialized view стара

SELECT cron.schedule FROM cron.job WHERE jobname ILIKE '%mv%'; — глянь чи cron активний. Force refresh: REFRESH MATERIALIZED VIEW CONCURRENTLY mv_paid_signatures;

"Permission denied for materialized view"

02.06.2026 anon/authenticated були revoked з MV. Доступ ТІЛЬКИ через RPC (dashboard_projects_with_stats(), is_paid_source()). Не намагайся в клієнті робити sb.from('mv_dashboard_projects_stats').

RPC timeout / 504

statement_timeout: anon=120s, authenticated=180s. Якщо RPC валиться по timeout — додай більше індексів або переключи на MV.

Фільтр не оновлює дані

З 02.06.2026 всі фільтри тригерять renderRoute() на change. Якщо не оновлює — перевір що ELEMENT id співпадає з addEventListener селектором.

IO storm у Supabase

Перевір розмір dashboard_webhooks (`pg_size_pretty(pg_total_relation_size('dashboard_webhooks'))`). Якщо > 100MB — webhooks_auto_cleanup_cron вимкнений. Запусти DELETE … WHERE received_at < NOW() - 14d.
