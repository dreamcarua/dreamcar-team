## 🐛 КРИТИЧНІ БАГИ ЗНАЙДЕНІ ТА ВИПРАВЛЕНІ

### Bug #1 — DO-блок test_pipeline впав через `compress_attempts`
**Симптом:** Вадим запустив SQL, але нічого не сталось у DCSMM.
**Причина:** test_pipeline SQL посилався на `compress_attempts` яка тільки в 016e існує.
**Fix:** Тестовий SQL переписано — використовує `BEGIN ... EXCEPTION WHEN undefined_column` для toleranсії.

### Bug #2 — claim_compress_jobs міг fail при 016e
**Симптом:** Postgres відмовляє `CREATE OR REPLACE FUNCTION` якщо змінено RETURNS TABLE структуру.
**Причина:** 016e додав `attempts int` у return → return type не співпадав зі старою функцією.
**Fix:** Додано `DROP FUNCTION IF EXISTS ...` перед CREATE.

### Bug #3 — Stuck "processing" rows назавжди
**Симптом:** Worker вмирає (ffmpeg crash) → row застрягає у processing → cron не може claim знов → пайплайн висить.
**Причина:** Worker мав `set -e` але без trap → exit без виклику fail_compress_job.
**Fix (1):** Worker додано `trap 'on_error $LINENO' ERR` — будь-яка помилка викликає fail_compress_job.
**Fix (2):** claim_compress_jobs тепер auto-recover stuck > 25min обʼяви назад у pending.

### Bug #4 — Autopost defer не працював
**Симптом:** Defer-логіка кидала PATCH на publications.publish_at, але claim не дивиться на publish_at → одразу claim знов.
**Причина:** `claim_autopost_jobs` не мав WHERE по publish_at.
**Fix:** 017 — додано `AND p.publish_at <= now()` і JOIN publications. Тепер defer реально затримує на 3 хв.

### Bug #5 — Autopost attempts++ при defer
**Симптом:** Кожен defer-цикл збільшував attempts. Після 3 defers (15 хв) черга позначалась як failed навіть якщо compress ще не готовий.
**Причина:** claim_autopost_jobs інкрементує attempts при кожному claim, defer не reset.
**Fix:** worker тепер при defer кладе `attempts: 0` назад. Defer більше не "спроба".

## 🎯 НОВІ ФІЧІ ДОДАНІ

### Feature #1 — Admin Compress Queue Dashboard
- Сайдбар → Адмін → 🎬 Compress Queue
- Показує всі video-creatives + статус + attempts + розміри H.264/HEVC
- Кнопка "↻ Re-compress" на кожному рядку
- Кнопка "click to retry all" на лічильнику Failed
- Auto-refresh кожні 15s
- Доступ: тільки CEO/COO/lead

### Feature #2 — HEVC (H.265) опційний варіант
- Worker з ENABLE_HEVC=1 створює другий варіант ~30-50% кращої якості при тому ж розмірі
- Зберігається у `compressed_url_hevc` поруч з H.264
- autopost з PREFER_HEVC=1 спробує HEVC, на error → fallback H.264
- Frontend може показувати обидва варіанти для порівняння

### Feature #3 — Error Recovery
- Compress worker: trap → fail_compress_job (raw)
- Autopost worker: trap → fail_autopost_job (raw)
- claim_*_jobs: auto-recovery stuck rows > 25-30 хв
- Worker exit codes тепер чіткі: 0 = OK, 1 = config/runtime error

### Feature #4 — Attempts tracking
- `creatives.compress_attempts` — лічильник, на 3-й спробі статус 'failed'
- `tg_autopost_queue.attempts` — defer не зараховується

## ⚠️ ВІДКРИТІ ПИТАННЯ

1. **Чи правильно cron */3 min для compress?** Великі відео (>10min) можуть не встигнути. Розгляну збільшення timeout до 35 min якщо побачимо crashes.

2. **Чи треба storage cleanup?** R2 росте з кожним відео — ~50MB × 30 креативів/міс = 1.5GB/міс. На Free tier R2 дає 10GB/міс = ~6-7 місяців. Потім $0.015/GB/міс.

3. **HEVC compat real-world?** Треба тестувати на різних TG клієнтах: iOS, Android (новий/старий), Web, Desktop. Якщо хоч 5% користувачів не побачать inline → відкатуємо.

4. **Brand book updates** (паузовані) — після стабілізації compress повернутись:
   - "квитки" → "токени"
   - "ви" → "Ви"
   - "Привіт" → "Доброго дня"
   - SLA "10 хв" → "30 хв робочий час"
   - Gender-neutral verb forms
